# Rate Limiting・IPブロック・プラグイン

## 方針と対象

ユーザー回答によりHTTP/HTTPSを先行し、TCP/UDP・Wasmを段階的に追加する方針を確定する。初期版の制限はEdgeごとのローカルな上限とし、クラスタ全体の厳密な上限とは呼ばない。複数Edgeへの分散により許容量は増える。全体上限が必要になった場合は別途分散カウンターを設計する。

Wasm導入の前に、組み込みポリシーで判定モデルを安定させる。管理者が設定するCIDRとドメイン単位ポリシーを対象とし、テナントによる任意コードのアップロードAPIは初期対象外。

## 実装単位

### B1: HTTPリクエスト単位の処理

- `listener.rs`のpeekによる解析をHyperのHTTP/1.1・HTTP/2処理に置換し、新設案`http_proxy.rs`に転送を分離する。既存のworkspace依存を活用し、必要なclient機能等をCargo.tomlへ追加する。
- HTTPリクエストごとにホスト名を正規化して認可・経路・ポリシーを評価する。重複Host、不正authority、SNIとHost/`:authority`の不一致を拒否する。
- 初期案は要求ごとにConnectorへのQUICストリームを開き、ローカルHTTPターゲットへHTTP/1.1として送る。HTTP/2の複数要求を独立して処理し、本文を全量バッファーせず背圧を伝える。
- hop-by-hopヘッダー処理、本文フレーミング、タイムアウト、ヘッダーサイズ、キャンセル、WebSocket Upgradeの引継ぎを実装する。CONNECTは明示対応まで拒否する。既存h2転送との互換性差分をE2Eで確認する。
- Towerを採用する場合はHyperのServiceとの境界にアダプターを置く。採用APIはPoCで確認する。[Hyper 1のServiceとサーバー構成](https://hyper.rs/guides/1/upgrading/)

完了条件: 同一keep-alive接続の複数要求、HTTP/2同時要求、分割ヘッダー、大きなストリーミング本文を正しく転送する。既存HTTP/TCP E2Eも通る。

### B2: 組み込みのIPブロック・Rate Limiting

- 新設案`policy.rs`に`RequestContext`と`Allow / Deny / RateLimited`を定義する。文脈は認可済みテナント、hostname、protocol、実クライアントIP、method、pathに限定する。
- IPは接続元を既定とする。LB配下では明示したtrusted proxy CIDRからの転送ヘッダーのみ解析し、右側から信頼境界をたどる。任意クライアントが渡したIPを制限キーに使用しない。
- 初期ルールはCIDRブロック→トークンバケットの順に評価する。キーは`tenant + hostname + client_ip`を既定とし、レートとburstを設定可能にする。allowlistを追加するならブロックとの優先順位を設定仕様に明記する。
- IPブロックは403、レート超過は429とRetry-Afterを返す。バックエンドへストリームを開く前に拒否する。WebSocketはUpgrade要求を数え、接続後フレーム単位の制限は対象外とする。
- バケットのTTL・最大件数・回収を実装する。容量上限で新規キーを無制限許可せず、容量超過として拒否して観測する。単調時計を使い、同時要求に対する消費を原子的にする。
- 設定案`policy.enabled / trusted_proxies / blocked_cidrs / requests_per_second / burst / max_entries`を検証する。設定再読込は全体を検証してから切り替え、失敗時は既存設定を保持する。

完了条件: burst境界・補充・同時要求で許可数が期待通りになる。IPv4/IPv6 CIDR、偽装ヘッダー、テナント分離、上限到達、再読込を検証する。拒否された要求がローカルターゲットへ届かない。

### B3: TCP/UDPへの拡張

- TCPは接続元CIDR、接続試行レート、同時接続数を制限し、終了時に必ず枠を解放する。HTTPの要求数とは別の設定・メトリクスにする。
- UDPは送信元・公開ポート単位のパケット数／バイト数を制限し、超過を破棄する。判定をタスク生成・返信マップ確保より先に行う。
- `tunnel.rs`のUDP返信マップにTTLと件数制限、送信失敗時の削除を追加する。無返信で状態が蓄積しないことを確認する。

完了条件: TCPの異常切断で枠が漏れず、UDP高負荷・無返信時にも状態数が上限内に収まる。

### B4: Wasmプラグイン

- 新設案`plugins/`にバージョン付きの入出力ABIを定義する。最初はB2と同じ文脈から許可／拒否を返すだけにし、本文書換えやソケット操作を含めない。
- Wasmtime等の実行系をPoCで選び、メモリ、実行時間、同時実行数、出力サイズを制限する。fuelまたはepoch interruptionで停止できる設計にする。[Wasmtimeの実行制御](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)
- ファイル・環境変数・ネットワークへの権限は既定で与えない。管理者が配置したハッシュ確認済みモジュールだけをロードする。
- ABI不一致・ロード失敗では直前の設定を保持する。実行時trap・timeoutは当該要求を503で拒否し、Edgeを停止させない。高速に旧世代へ戻せるようにする。

完了条件: 無限ループ、メモリ超過、不正出力、未許可I/Oが隔離され、別テナントや組み込みルールが影響を受けない。

## 検証・導入

決定的な仮想時計でバケットを単体検証し、HTTPS/h2/Upgrade、信頼プロキシ、TCP/UDPのE2Eを追加する。導入は判定のみを記録する監視モードから始め、対象ドメインごとに強制へ切り替える。拒否理由、判定時間、バケット数、プラグイン失敗数を観測する。メッシュ導入後も入口Edgeで一度だけポリシーを適用する。
