# 公開サーバー間の内部転送メッシュ

## 方針と設計判断

ユーザー回答により、**将来の標準構成としてEdge間転送へ移行する**方針を確定する。標準の経路は「入口Edge→Connector接続先Edge→Connector」とし、ローカルにConnectorがあれば直接転送する。README第1.1節・第3.1節の「Edge間転送なし」は、実装に合わせて新しい設計思想・トポロジへ改訂する。

初期版は1ホップの転送に制限する。経路探索による多段メッシュは含めない。移行期間はConnectorがすべてのEdgeへ接続する従来構成を維持し、転送の検証完了後に接続先を一部Edgeへ減らす。標準化後は全EdgeへのConnector接続を不要とし、複数Edge構成では冗長な接続先を設定する。従来構成は明示的に選べる互換モードとして残す。

## 実装単位

### M1: 信頼境界と接続プロトコル

- `config.rs`へ固定`edge_id`、専用listen/advertiseアドレス、peer一覧、CA・証明書・秘密鍵、接続上限を追加する。自己ID重複・広告アドレス不備を起動時に検証する。
- 新設案`mesh/transport.rs`に専用QUICエンドポイントを実装する。Connector用とは別ALPN・メッセージ体系にし、mTLSで証明書のEdge IDと許可peerを照合する。
- 既存のConnector用サーバー検証省略を流用しない。関連改善としてConnector側にもCA検証またはピンニングを導入し、移行設定・誤証明書拒否をテストする。
- 新設案`sievetube-common/src/mesh_protocol.rs`にversion、入口edge_id、tenant_id、hostname、protocol、client_addr、request_id、残りホップ数、接続世代を含む転送要求と受入応答を定義する。
- peer認証だけで任意テナントへ転送可能にせず、受信Edgeがhostnameとtenantの所有関係およびローカルConnectorを検証する。長さ上限・タイムアウト・未知versionの拒否を実装する。

完了条件: 未許可peer、証明書不一致、Connector用ALPN、不正テナント、過大フレームを拒否する。既存`sievetube/1`プロトコルへの変更は不要な設計とする。

### M2: 経路広告・リース・ローカルキャッシュ

- `valkey.rs`にEdge生存リースと`hostname + protocol + tenant + edge + connection_generation`の経路広告を追加する。現在のtenant→Edge集合だけでは到達アドレスも生存性も判断できない。
- 経路は認証済みConnectorの登録後に広告し、接続終了時は一致する世代だけを削除する。TTL更新、再起動、旧プロセスの遅れた削除を検証する。
- 新設案`mesh/routes.rs`で周期同期し、通知があれば更新を早める。通知だけに依存せず、転送時は有効期限内のローカルキャッシュを検索する。Valkeyへ本文を送らない。
- `router.rs`の戻り値を`Local / Remote / Unavailable`相当にする。ローカル優先、遠隔候補は安定した順序で選び、失敗peerは一定期間候補から外す。
- Valkey停止中も有効なキャッシュを使えるが、期限切れ遠隔経路は使用しない。ローカルの認証済み接続は継続可能とし、新規所有権取得・遠隔経路広告は停止する。

完了条件: Edgeが異常終了してもTTL後に経路が消える。再接続した新世代が旧接続の終了で消えない。制御系停止がローカル転送を即時停止させない。

### M3: HTTP/HTTPS・TCPの1ホップ転送

- `tunnel.rs`を転送先抽象へ対応させ、Remoteの場合はpeerへストリームを開く。受信Edgeは必ずローカルConnectorだけへ送り、再転送要求を拒否する。
- 入口で[B2のポリシー](02-traffic-policy.md)を一度適用する。受信Edgeは転送権限を検証し、入口から来たIP等を認証済みpeerのメタデータとして扱う。
- 受入確認前の失敗だけ別候補へ再試行できるようにする。本文送信後や受入状態不明の要求は自動再送せず、POSTなどの重複処理を防ぐ。
- 半閉鎖、背圧、キャンセル、長時間ストリーム、終了時のdrain期限を実装する。HTTPでは応答開始前の経路不在・失敗を502、接続待ちタイムアウトを504として扱い、開始済みならストリームを終了する。TCPでは切断する。
- peer単位・テナント単位の同時ストリーム上限と待機時間を設ける。全peerの無制限な接続生成を防ぐ。

完了条件: ConnectorがEdge Bにしか接続していなくても、Edge AからHTTP/HTTPS/TCPが届く。第三のEdgeを加えた循環経路、B停止、POST途中切断で再転送ループ・重複送信がない。

### M4: UDP転送と運用構成

- `mesh_protocol.rs`へversion付きデータグラムを追加する。入口Edge ID・接続世代・request_idの複合キーで応答先を区別し、複数入口のID衝突を防ぐ。
- 初期版は現行UDPの「1要求1応答」を維持すると明記する。複数応答・長寿命フローを必要とする用途は別のセッション設計後に対応する。
- 両QUIC区間の送信可能サイズからヘッダー分を引いた上限を検証する。初期版は独自分割をせず、超過データグラムを破棄・計測する。
- 返信マップのTTL・件数上限・送信失敗時の回収を実装し、未知IDや期限切れ返信を捨てる。UDPメッシュ未対応peerへUDP経路を広告しない。
- Connectorの接続先を一部Edgeに絞る設定例と、従来の全Edge接続へ戻す手順を追加する。縮小後も単一接続先の障害を避けられるよう、複数接続先でフェイルオーバーを検証する。

完了条件: 2入口から同時にUDP送信して返信が混線しない。無返信・サイズ超過・peer切断時の状態数が上限内に収まる。

### M5: 標準構成への移行

- M1〜M4の完了、HTTP/HTTPS/TCP/UDPの回帰、peer・接続先Edge障害からの復旧、性能基準の達成を既定切替の条件とする。移行期間の既定無効は段階導入のための措置とする。
- 設定案として構成バージョンと`routing.mode = "mesh" | "direct"`を設ける。新しい構成バージョンと生成する設定例ではmeshを既定にする。旧設定はdirectとして解釈して移行案内を出し、アップグレードだけで通信経路を変更しない。
- 複数Edgeのmesh構成ではValkey、固定Edge ID、相互認証、peerの到達性を必須の運用要件として検証する。不足時に黙ってdirectへ切り替えず、設定エラーとして明示する。単一Edgeのdirect構成も文書化する。
- 先にEdge群を更新してpeer接続・経路広告を確認し、Connectorの全Edge接続を維持したまま一部ドメインで遠隔転送を検証する。その後、Connectorの接続先を冗長な部分集合へ減らす。旧Edgeが混在する間はそのEdgeへの直接接続を維持する。
- README第1.1節・第3.1節・第3.2節・第7節、Edge/Connector設定例、運用手順を更新する。標準の経路、制御系停止時の挙動、既存ストリームは障害時に引き継げないこと、新規接続の復旧条件を記載する。

完了条件: 新規設定でメッシュ構成を構築でき、旧設定では従来動作が保たれる。既存構成からの段階移行とdirectへの切戻しをE2Eで検証し、標準構成の説明と実際の既定値が一致する。

## 検証・導入

`tests/integration/tests/e2e_mesh.rs`と複数Edge・Valkey・テストCAのハーネスを追加する。正常転送、所有権競合、旧世代削除、ネットワーク分断、Valkey再起動、peer証明書更新を検証する。

移行期間の既定無効→一部ドメインの遠隔転送→複数入口→UDP→M5の標準構成への切替の順で導入する。遠隔転送数、peer接続、経路期限切れ、ホップ違反、転送失敗、追加遅延を観測する。復旧時はまずConnectorを全Edgeへ再接続し、ローカル経路の準備を確認してからdirectへ切り替える。既存ストリームにはdrain猶予を与え、期限到達後にpeer接続を閉じる。
