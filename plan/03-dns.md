# DNSレコードの自動登録・更新

## 方針と対象

DNSの権威サーバー運用は外部へ委譲したまま、プロバイダーAPIによるレコード管理だけを追加する。初期版は管理者が設定したA・AAAA・CNAMEを対象とし、ConnectorのNAT内アドレスを公開しない。EdgeまたはLBの公開先を明示設定する。

ユーザー回答によりCloudflare・Route 53の両アダプターを実装対象とする。実際の利用先は未定だが、D1の共通層に続いて両方を実装し、共通の契約テストを適用する。ACMEはHTTP-01を基本とし、DNS-01を後続段階で両プロバイダーに対応させる。SDKのバージョンは実装時に公式資料を確認して決定する。

## 実装単位

### D1: 望ましい状態とプロバイダー境界

- 新設案`sievetube-edge/src/dns/mod.rs`にレコード一覧取得・作成・更新・条件付き削除のインターフェースとモックを定義する。プロバイダーが条件付き操作を持たない場合の再取得・競合検知を明示する。
- 設定案は`dns.enabled / providers / records`。名前付きプロバイダー設定に種別・zone_id・認証方法を持たせ、各レコードから参照する。同一プロセスで両プロバイダーの別ゾーンを管理できるようにする。各レコードはhostname、type、values、TTLを持つ。認証情報の値自体をTOMLへ埋め込まず、環境変数またはファイル参照で受け取る。
- 管理者の許可ゾーンとP0の所有権に照らして入力を検証する。CNAMEと同名の他レコード、プロバイダー固有のapex制約、重複・不正TTLを検出する。
- dry-run差分を出力するreconcile処理を作る。管理レコードID、以前の値、管理世代を永続化し、既存の非管理レコードがあれば競合として停止する。明示的な取り込み手順を別に設ける。

完了条件: 同じ設定を繰り返し適用して差分が消える。他ツールが管理するレコードを上書き・削除しない。

### D2: Cloudflare・Route 53と定期更新

- `dns/providers/cloudflare.rs`と`dns/providers/route53.rs`を別PRで追加し、両方でページング、レート制限、タイムアウト、認証期限切れ、部分成功を扱う。片方だけの完了ではD2完了としない。
- 複数Edgeから同一レコードへ書き込まないよう、ゾーン単位の期限付きリースを使う。旧世代の書込みを拒否できるよう世代を記録する。Valkeyなしでは明示的な単一書込み担当モードのみを許す。
- 期待状態と実状態を周期比較して必要な差分だけ適用する。書込み直後の読取りが遅れる場合を考慮して再試行間隔を設ける。
- 初期版は短時間のConnector切断でDNSを書き換えない。公開先の変更は明示設定で行う。ヘルス連動を後で追加する場合は連続失敗閾値・復帰待機・最小更新間隔を別に設計する。
- 削除は設定から消えたという理由だけでは行わず、削除指定と管理ID・現在値の一致を確認する。外部変更を検知したら競合として停止する。

完了条件: Cloudflare・Route 53それぞれのテストゾーンで作成→値変更→再実行→管理対象削除が通る。API停止・担当交代・部分失敗から復旧し、既存の非管理レコードを維持する。

#### D2-CF: Cloudflare固有の処理

- ゾーン内のDNSレコードIDを永続化し、同名・同種の複数レコードを共通層の値集合へ正規化する。ゾーンを限定したAPIトークンに必要なDNS読取り・書込み権限を与え、環境変数またはファイルから取得する。[DNS更新API](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/edit/)
- 管理対象の通常レコードはDNS-onlyを初期値とする。既存レコードを明示的に取り込む場合はプロキシ設定を保持し、DNS値の更新で意図せず変更しない。プロキシ有効時のHTTP-01検証経路は運用手順で確認する。
- API書込み成功とDNS伝播完了を区別する。複数レコード更新途中の失敗は差分を再取得して回復し、外部変更との競合を検出する。

#### D2-R53: Route 53固有の処理

- public hosted zoneを対象とし、ゾーン・名前・型でレコード集合を識別する。初期版は単純なA・AAAA・CNAME・TXTを扱い、Aliasやweighted/failover等のルーティング設定は取り込まず、未対応として明示する。
- `ChangeResourceRecordSets`で作成・更新・削除し、返却された変更IDを保存する。`GetChange`のPENDING/INSYNCを追跡し、再起動後も未完了変更を確認する。INSYNCでも再帰DNSキャッシュの更新完了を意味するとは扱わない。[変更API](https://docs.aws.amazon.com/Route53/latest/APIReference/API_ChangeResourceRecordSets.html)、[変更状況API](https://docs.aws.amazon.com/Route53/latest/APIReference/API_GetChange.html)
- AWS認証はSDKの標準認証情報取得を利用し、ロール・一時認証情報を利用できるようにする。対象ゾーンの一覧取得・変更と変更状況取得に必要なIAM権限を設定例に記載する。AWS資格情報をCloudflareの単一トークン形式へ無理に共通化しない。
- TXTはRRset全体の値を扱うため、同名の既存値を保持して必要な値だけを追加・削除する。外部書込みとの完全な排他は仮定せず、管理権限の分担と競合時停止を運用条件にする。

### D3: ACME DNS-01用TXT操作

- A/AAAA/CNAMEの望ましい状態と、期限付きTXTチャレンジを別の用途・状態として管理する。
- `_acme-challenge`のTXT値を追加し、プロバイダーの反映状況とDNS応答を確認してからACME検証へ進む。固定sleepだけを成功条件にせず、上限時間を超えれば注文を失敗として扱う。
- 同名の複数TXT値を保持し、完了・失敗後に当該注文が追加した値だけを削除する。再起動時には永続状態から未完了操作を回収する。
- CNAME/NSによる検証先委譲は管理者が許可したゾーンだけを追跡する。ワイルドカードと通常名の同時検証で互いのTXTを消さない。[Let's Encrypt DNS-01仕様説明](https://letsencrypt.org/docs/challenge-types/)

完了条件: 両プロバイダーでTXTの追加・伝播待ち・検証・清掃が正常系／失敗系とも通り、別注文や運用者のTXTを残す。[ACME計画](01-acme.md)のA3と結合する。

## 検証・運用

通常CIはモックAPIでページング、競合、429、遅延、タイムアウトを再現する。実APIの検証は専用テストゾーン・限定権限で別実行にする。APIトークンのログ出力を検査し、dry-runの差分が秘密情報を含まないことも確認する。

更新成功・失敗、差分残数、競合、最終同期時刻を監視する。DNS TTLのため更新・切戻しは即時には全クライアントへ反映されない。ロールバックは自動同期を停止したうえで保存した以前の管理値を再適用し、現在値が外部変更されていれば自動復元を止める。
